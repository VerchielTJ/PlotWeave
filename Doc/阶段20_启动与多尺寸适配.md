# 阶段20：启动与多尺寸适配

本阶段补齐“打开剧情编辑器”到实际可输入制作状态的启动路径，并检查原制作布局在不同Game视图尺寸下的可见性与操作性。它承接[阶段19](阶段19_制作输入与内嵌试跑.md)的工作副本输入、内嵌试跑和显式表格交换，不把阶段19的23项结果扩大为本轮新增代码已验收。

## 启动方式

使用 `Tools / PlotWeave / 打开剧情编辑器`。主入口优先使用有效的本地原制作场景；没有本地迁移场景时，使用公开通用制作场景，已有样例不会因每次打开而重新生成。入口自动进入Play Mode并显示Game视图，节点录入与试跑均在Game视图中操作。

已有可用制作会话时，重复执行主入口只聚焦Game，不重新打开场景。当前运行无关场景时会明确提示先退出Play Mode；当前场景的保存/切换被取消时不进入Play。Unity预设了其他Play Mode起始场景时，本次显式制作启动临时使用制作场景，切换完成或失败后恢复原设置。

需要查看场景层级或静态布局时，可使用 `Tools / PlotWeave / 本地原布局 / 打开制作界面` 或 `Tools / PlotWeave / 制作工具 / 打开UGUI制作场景`。这两个菜单仅打开场景并显示一次轻量启动窗口，点击“进入剧情制作（Play）”后才启动制作。直接双击场景资产保持普通EditMode预览，不会自动初始化编辑事务或弹出启动窗口。

## 静态画面裁切的原因与修补

本次用户反馈截图来自尚未初始化的EditMode原场景。保存场景的 `CanvasScaler` 使用 `ConstantPixelSize`、缩放1、参考尺寸800×600，而布局按3200×1500制作。原宿主只在Play Mode初始化时改成 `ScaleWithScreenSize` 与 `Expand`；原主入口仅打开场景时，输入工具栏、运行期缩放及真实控件接线尚未建立，因此静态画面会表现为巨大裁切并保留默认占位项。

多尺寸复查还发现一处坐标基准错误：把原中心锚点的偏移当作底边偏移，在父面板改为随窗口拉伸后，底栏和右栏会随高度错位。当前 `AnchorFromReference` 按原3200×1500参考坐标转换到对应锚点，再由 `StretchRightColumn` 保留右栏宽度并随面板高度拉伸；底部输入与起点、播放、刷新入口维持各自的布局基准。

主入口自动进入制作状态是正常使用路径。另提供显式菜单 `Tools / PlotWeave / 制作工具 / 修正本地制作场景静态缩放`，用于把已登记的本地迁移场景保存为3200×1500、`ScaleWithScreenSize`、`Expand`，使静态预览也使用相同缩放基准。它只调整生成场景的CanvasScaler，不在EditMode初始化会话。

`PlotAuthoringSceneLayoutRepair` 执行前要求退出Play Mode、所有已加载场景均无未保存修改，目标位于登记的本地原布局目录，且当前场景磁盘SHA与上轮工作流证据一致。它先备份场景及meta到 `Library/PlotWeaveRecovery/StaticLayout/<id>`，再仅保存目标场景，记录前后SHA及修补结果；遇到用户已保存修改或证据不符时拒绝覆盖。原 `I:\model` 不在修改范围。

静态缩放修补已显式执行并保留[备份与前后SHA记录](Records/Stage20/2c628143a7474bc4b85a42a616ae2d3d/static-layout.json)，修补ID为 `2f5e5d94562e4ffa9d5a51943b53157b`。这是矩阵探针开始前的独立、有意场景改动；后文“源不变”和“零保存”仅描述矩阵探针过程，不包含这次修补。静态画面可见不等于输入事务已初始化，实际录入仍从制作入口进入Play。

## 初始化状态与失败处理

原制作宿主只有在会话、节点控件、预览区域以及播放、刷新、关闭和工作区交换回调全部接线成功后，才设置 `InitializationReady`。启动入口以该状态判断是否可以直接聚焦现有制作会话。

初始化异常时释放工作副本、关闭已创建预览、清除制作入口委托，并记录 `InitializationError`。失败界面显示只读提示，同一失败实例不会逐帧重新初始化；用户草稿保留。检查Console并修复原因后，退出Play Mode再重新进入制作。

新建公开工作区时仍按原资产顺序验证并创建枚举、Bean、表头、节点、对话、常量和演员表，保存只针对本次新建的资产，不触发全局 `SaveAssets`。

## 视口、节点列表与弹层

`PlotAuthoringViewportLayout` 在原制作布局上协调工具栏、节点列表、内嵌预览和底部输入。它根据Canvas实际缩放调整工具栏、起点/播放/刷新和KEY控件的尺寸与排列，并调用真实的 `PlotNodeView.ConfigureDisplay` 配置逻辑行高和最小字号；面板尺寸变化时调用宿主的 `RefreshInputDock` 重新计算输入停靠。空预览区采用中性背景并显示“选择节点后点击播放”的提示，重复的对白保存按钮隐藏，保留顶部统一保存入口。原布局分区职责来自原设计，这些密度和尺寸策略是当前协作新增。

`PlotNodeView` 继续只为可见节点维护按钮池。`ConfigureDisplay` 调整行高时先记录原逻辑滚动首行，再按新行高恢复位置并刷新可见按钮，不会为全工作区节点创建控件，也不会在每次尺寸变化时强制滚回首行。该池化实现属于当前迁移代码，不能由节点选择的原设计推断原版已有相同算法。

`PlotAuthoringPopupLayout` 接管原参数及列表弹层的显示边界。它保持控件原有的RowUnit或滚动层级，提升当前弹层的绘制顺序，结合画布、面板、祖先Mask和顶部工具栏计算安全区域，再缩放及夹取弹层。当前新增关闭按钮，并按物理像素目标保护关闭入口；关闭后恢复原位置和缩放。原参数/列表编辑职责沿用，自动适配与关闭入口属于本轮补齐。支持范围内的几何、遮挡及点击检查已通过，小尺寸密度结果单独保留。

真实列表另有两项已修复的问题：横向stretch的行仍保留700逻辑单位的宽度增量，导致第二列进入Mask外；复杂Bean超过原两排单元格时，沿用176逻辑单位的固定行高会让相邻行重叠。宿主的private辅助方法 `PrepareListRow` 现在把stretch宽度增量设零，先绑定真实成员再测量Grid的preferredHeight，使用测得高度排列与复用可见行；空列表也会清理可见控件和滚动内容。

交互夹具同步修正了渲染时序：新增行或打开弹层后，等待真实Canvas渲染，再进行射线命中检查，确保Graphic已具有有效depth。该等待用于消除尚未渲染控件造成的误判；列表宽度与复杂Bean行高的修复由新增两个真实布局用例单独验证。

当前代码把1024×600作为制作窗口策略下限，低于宽或高任一条件时显示扩大或最大化Game视图的提示。这个提示不会自动扩大窗口。900×600与720×900的实测密度不足已在报告中保留，不计作支持通过。1024×600是声明的下限；本次直接实测下列四个支持尺寸，没有用离散矩阵推定所有连续宽高组合均已验证。
